## 1. 总体技术架构 (Technical Architecture)

### 1.1 架构拓扑

采用 **前后端分离 + 微服务模块化** 架构。

* **客户端**: 微信小程序 (Uni-app 编译)，分包加载。
* **接入层**: Nginx (反向代理 / SSL / 静态资源缓存)。
* **应用层**: Node.js (NestJS Framework)，无状态服务，支持水平扩展。
* **数据层**:
* **MySQL 8.0**: 核心业务数据（用户、内容、关系）。
* **Redis 6.0**: 缓存（Session、验证码、Feed流热数据）。
* **OSS (对象存储)**: 存储图片、视频文件，配置 CDN 加速。


* **第三方服务**: 微信 API (登录/支付)、阿里云/腾讯云 (短信/内容安全)。

### 1.2 目录结构规范

## 2. 核心模块研发需求 (Module Specifications)

### 2.1 认证与用户模块 (Auth & User)

* **研发目标**: 实现“静默登录 + 强制实名”的漏斗机制。
* **技术逻辑**:
1. **JWT 机制**: 登录成功返回 `access_token` (7天) 和 `refresh_token`。所有非公开接口需通过 `JwtAuthGuard`。
2. **数据加密**:
* `mobile`: 使用 **AES-256-CBC** 加密存储，密钥存放在环境变量，数据库中不可见明文。
* `password` (若有): 使用 **Bcrypt** 加盐哈希。


3. **适老化配置**: 在 `users` 表增加 `font_scale` 字段 (Default: 1.0)。前端启动时拉取该配置并应用到 CSS Variables。



### 2.2 内容发布与审核系统 (Content & Audit)

* **研发目标**: 确保所有 UGC 内容经过“机审+人审”闭环。
* **状态机设计 (State Machine)**:
* `0 (PENDING)`: 待审核 (仅作者可见)。
* `1 (PUBLISHED)`: 已发布 (公开可见)。
* `2 (REJECTED)`: 驳回 (作者可见，需附带 `reject_reason`)。
* `-1 (DELETED)`: 用户删除 (软删除)。


* **发布流程**:
1. 前端直传 OSS，获取 URL。
2. 后端接收 Post 数据，写入 DB (`status=0` 审核中)。
3. **人工审核**: 内容进入后台管理待审核列表，由管理员手动审核。
* 通过 -> 更新 `status=1` (已发布)。
* 驳回 -> 更新 `status=2` (驳回)，填写驳回原因供作者查看。
* 删除 -> 更新 `status=-1` (软删除)。
4. **API审核设计（暂不实现）**: 已设计好异步队列架构和第三方API对接逻辑，保留在代码中，后续可通过配置开关快速启用机审功能，实现"机初审+人复审"的升级流程。





### 2.3 首页推荐流 (Home Feed)

* **研发目标**: 高性能的混合内容流分发。
* **算法逻辑**:
* **SQL 基础查询**:
```sql
SELECT * FROM posts 
WHERE status = 1 
AND user_id NOT IN (blacklist_ids)
ORDER BY (created_at > NOW() - INTERVAL 3 DAY) DESC, -- 优先3天内
         (view_count + like_count * 5) DESC -- 热度降权
LIMIT 10 OFFSET N

```


* **缓存策略**: 首页前 5 页数据缓存至 Redis `feed:recommend:cache`，TTL 10分钟。


* **前端优化**: 使用 `u-list` 或 `virtual-list` 组件，防止长列表 DOM 节点过多导致低端机卡顿。

### 2.4 视频沉浸流 (Video Player)

* **研发目标**: 仿抖音交互，流畅播放。
* **技术实现**:
* 组件：使用 Uni-app 原生 `<video>` 组件（层级最高，注意覆盖问题）。
* **预加载**: 监听 `swiper` 的 `change` 事件。当滑到 Index=1 时，静默加载 Index=2 的视频资源。
* **流量保护**: 监听 `uni.getNetworkType`。非 Wifi 环境且未授权流量播放时，自动暂停并弹窗。

## 4. 接口规范 (API Specification)

**Base URL**: `https://api.silverhealth.com/v1`

### 4.1 响应包装 (Response Wrapper)

```typescript
interface ApiResponse<T> {
  code: number;      // 0:成功, >0: 业务错误
  msg: string;       // 提示信息
  data: T | null;    // 业务数据
  timestamp: number; // 毫秒时间戳
}

```

### 4.2 关键接口定义

| 模块 | 方法 | URI | 描述 | 参数示例 |
| --- | --- | --- | --- | --- |

## 5. 非功能性需求 (NFR)

### 5.1 性能要求

* **API 响应时间**: 95% 的请求需在 **200ms** 内返回（不含网络传输）。
* **首屏渲染 (FCP)**: 小程序冷启动耗时 < **1.5s**。
* **长列表性能**: Android 低端机 (骁龙6系) 滑动帧率 > **45 FPS**。

### 5.2 安全要求

* **SQL 注入**: 严禁拼接 SQL，必须使用 TypeORM Repository API。
* **XSS 防御**: 富文本展示端使用 `mp-html` 组件，并配置白名单过滤。
* **鉴权**: 所有写操作接口 (POST/PUT/DELETE) 必须校验 Token。

### 5.3 适老化特殊要求

* **点击热区**: CSS 中所有 `Clickable` 元素增加 `padding: 10px` 或设置 `min-width/height: 44px`。
* **字体缩放**: 必须支持 CSS Variable 动态调整，最大支持 1.4 倍放大，且布局不崩坏（使用 Flex/Grid 布局，避免固定高度）。
